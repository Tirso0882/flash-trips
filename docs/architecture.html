Identity and persistence details

JwtAccessTokenVerifier in src/flash_trips/adapters/identity/access_tokens.py verifies signed access tokens against an issuer, audience, access-token claim contract, required scope, asymmetric algorithm allowlist, and served JWKS. It also rejects a token carrying ID-token claims. JWKS retrieval uses only the configured HTTPS destination, bounded by the versioned JwksFetchPolicy in src/flash_trips/adapters/config.py for timeout, response size, cache lifetime, and refresh rate. Rotation replaces retired cached keys, while neither an unknown key ID nor a failing issuer can refetch faster than that refresh interval. These boundaries are proven against the deterministic TLS local issuer in tests/identity/. When the complete Entra environment is present, create_runtime_app composes this verifier with the exact tenant issuer, client audience, and tenant JWKS. Missing provider configuration retains the fail-closed RejectingAccessTokenVerifier.

The PostgreSQL adapter implements the principal-scoped Planner repository and unit of work. It also resolves only an exact issuer and subject pair from external_identities to an active Planner. The runtime composition validates the configured single-entry allowlist and connects that resolver to the protected route. The linear, reversible Alembic history also creates application_sessions, which stores only a keyed digest of each opaque browser identifier and an encrypted exact-audience access token. The BFF session manager in apps/web/lib/server/session.ts enforces idle and absolute expiry, revocation, origin validation, and session-bound CSRF. It reaches that table over its own PostgreSQL connection from apps/web/lib/server/session-runtime.ts rather than through FastAPI, so the web process needs DATABASE_URL as well as the API base URL. The auth sign-in, callback, session, and sign-out routes use the shared cookie policy. The callback validates an encrypted, short-lived state, nonce, PKCE verifier, exact redirect, token response, and signed ID token before creating the application session. Provider tokens never enter the browser. The JSON logger, Key Vault access, and Application Insights resources are not connected.

src/flash_trips/application/trip_planning.py owns Trip create, list, and read use cases through the principal-scoped UnitOfWork. The PostgreSQL adapter stores the ownership root in trips and each ordered city stay in trip_structures. Both carry the owning Planner reference. FastAPI exposes /api/v1/trips, and apps/web/app/api/trips/route.ts forwards only the server-held access token after application-session and CSRF checks. Foreign and absent Trip identifiers return the same problem response.

The same application interface starts and reads principal-scoped Runs. PostgreSQL stores each Run in runs, seals its first terminal outcome, and uses a partial unique index to allow only one active mutating Run per Trip.

A successful Run uses that same UnitOfWork transaction to insert one complete plan_revisions snapshot and its evidence-backed plan_claims, then seal the Run outcome. PlanRevisionRepository exposes commit and current read operations only. The mutable trips.current_plan_revision_id head changes in the same transaction. PostgreSQL rejects updates to both immutable tables and permits at most one revision per Run. FastAPI exposes the authoritative current snapshot at /api/v1/trips/{trip_id}/plan-revision.

Committing that revision also presents one immutable approval_requests record through the ApprovalRepository. The versioned Approval command accepts only an Approval Request identifier paired with its exact Plan Revision identifier. PostgreSQL rechecks the owning Planner and current revision before inserting one immutable approvals record. Missing, foreign, mismatched, and superseded bindings all fail as the same typed not-found problem. The Next.js BFF requires the session-bound CSRF token before forwarding the bound action.

An approved current revision can be compiled through TripPlanning.compile_current_handbook. The format-neutral compiler in src/flash_trips/platform/handbook/ produces a schema-versioned Handbook Document, and its deterministic HTML renderer escapes untrusted claim text. PostgreSQL stores the exact bytes and checksum in immutable handbook_snapshots, bound to the owning Planner, Plan Revision, and qualifying Approval. The authenticated /api/v1/handbook-snapshots/{snapshot_id}/export endpoint rechecks ownership and records one immutable handbook_deliveries row for each authorised retrieval. A Delivery is neither an Approval nor proof that the file was opened. The Next.js BFF keeps the access token server-side for compilation and download.

Architecture slots

The kernel now owns the typed Capability contract, and Travel Readiness contains the one fixture-backed skeleton implementation. The other Capability and platform packages remain empty package markers. The Planner page contains the thin Trip, Run, Plan Revision, Approval, and Handbook stations; the Operator page remains a shell. The contract stays in src/flash_trips/kernel/, the only module both flash_trips.application and flash_trips.capabilities may import under .importlinter.

Fail-closed defaults

The default access-token verifier rejects all tokens. Live provider and model calls have zero authority. Production does not currently provision PostgreSQL or inject application secrets.

Delivery order

Feature work is sequenced by ADR 0021 rather than by finishing each Feature before the next begins. E-SKELETON (issue 261) fills the architecture slots thinly first, in one chain of seven Tasks, producing a browser-asserted path through sign-in, Trip, Run, Plan Revision, Approval, and Handbook download with fixture-backed results at every station. The FT-* Features then deepen each station against a running system and keep their existing registry ownership.

The browser harness and its sign-in, Trip, Run, Plan Revision, Approval, and Handbook download stations now exist in tests/journey/. It seeds two synthetic Planners. The positive journey completes every station, while the unauthorised journey proves the second Planner is refused at the first foreign station. The full matrix in tests/security/ covers unauthenticated and Operator credentials plus indistinguishable foreign and missing resources. Revoked and expired application sessions are exercised at every BFF station by tests/journey/session-revocation.journey.mts and the session-manager matrix in tests/web/. This is current behaviour established by ADR 0021. The journeys, denial matrix, and Evaluation Fixtures are permanent. The thin fixture-backed implementations are planned work, not complete product depth, and each carries an in-code marker naming the open FT-* Feature that replaces it.

Current status request

This is the fully implemented end-to-end path and the best starting point for learning how contracts, the BFF, HTTP adapters, and application interfaces fit together.

  1. The browser requests GET /api/status from the Next.js application.
  2. The BFF resolves FLASH_TRIPS_API_BASE_URL and creates the generated @flash-trips/api-client.
  3. The client calls FastAPI at GET /api/v1/status.
  4. The HTTP adapter calls TripPlanning.service_status() through the application interface.
  5. StaticServiceStatus returns the kernel model. FastAPI serializes it using the canonical Pydantic contract.
  6. The BFF returns the same JSON. Backend failures become a stable application/problem+json response with a request ID.

Current Trip request

This path proves private Trip persistence through the browser, BFF, generated client, application facade, and real PostgreSQL.

  1. The Planner page obtains the session-bound CSRF token and reads GET /api/trips.
  2. The BFF authorizes the opaque application-session cookie. Create additionally checks the exact origin and x-flash-trips-csrf.
  3. The BFF maps the single-city form to the collection-shaped generated contract and calls /api/v1/trips with the server-held access token.
  4. FastAPI resolves the active Planner and calls TripPlanning. No Planner identifier comes from the browser request.
  5. The principal-scoped repository writes or reads trips and ordered trip_structures rows in one unit of work.
  6. Reloading the Planner page lists the canonical row again with the same opaque Trip identifier.

Current Run request

This path proves one durable, principal-owned Run and one sealed terminal outcome using the permanent Travel Readiness Evaluation Fixture.

  1. The Planner starts a Run through POST /api/trips/{tripId}/runs. The BFF validates the application session, origin, and CSRF token.
  2. The generated client calls POST /api/v1/trips/{trip_id}/runs with only the server-held access token and Trip identifier.
  3. TripPlanning verifies ownership, inserts the active Run, and invokes the injected fixture Capability from capabilities/travel_readiness/.
  4. The principal-scoped Run repository conditionally records the first terminal outcome. A later terminal write cannot overwrite it, and the database rejects another active Run for the Trip.
  5. The browser reads GET /api/runs/{runId}, which forwards to GET /api/v1/runs/{run_id}, and displays the terminal status.

Sandcastle delivery loop

The host process owns tracker and publication writes. Agents work in Docker sandboxes and only produce commits plus validated output. Independent Tasks can run concurrently, up to three at a time. The integration agent merges the run's pinned main commit before reviewed Task commits, keeping long-lived Feature branches current without rewriting their published history. .sandcastle/run-state.json durably records claimed, reviewed, integrated, and published checkpoints. Recovery resumes reviewed work at integration and retries publication from its verified integration commit before planning new Tasks. Paid implementers use one non-resumable session with a direct-execution prompt. The default run limits are one concurrent Task, five Tasks, and 120 minutes.

Authority rule: applying agent:autopilot to a Feature authorizes repeated Task claims, spending, branch publication, and pull-request updates. Remove it to stop new claims. An already claimed Task finishes. Interruptions before review still block the Task for inspection. An empty implementer exit is not retried automatically. Reviewed and integrated checkpoints remain agent:in-progress so the next run can resume without paying for implementation or review again.

CI and Azure production

During E-SKELETON, T-01 adds a separate disposable Azure feedback environment from infra/azure/skeleton.bicep. It exposes the web/BFF over HTTPS, keeps FastAPI internal, uses one low-cost PostgreSQL server, and grants no model or travel-provider authority. The walking-skeleton job in .github/workflows/quality.yml runs only after all CI jobs pass on the E-SKELETON Feature branch, updates both apps, migrates PostgreSQL, and smoke tests the public BFF boundary. The deeper Feature implementation and the production path shown below remain deferred and unchanged.

Pull requests and main run five required CI checks. Dedicated denial and journey checks protect the negative and positive walking-skeleton paths. The quality job depends on both, scans Git history for secrets, then runs the complete repository checks and web build. The other required checks are containers and traceability. After successful main CI, a release plan continues only when production image inputs changed. Release and deployment use separate secretless GitHub OIDC identities with narrow Azure roles.

Current artifact flow: CI builds and smoke-tests local images. After main CI, the production workflow skips documentation, test, infrastructure, CI, and agent-only commits. Qualifying or manually requested releases rebuild both images from the selected main commit before publishing digests. The CI-built image objects themselves are not promoted.
