# Expose typed commands, queries, and durable Run observation

Flash Trips will expose a versioned JSON/HTTP application API with explicit use-case commands, authoritative queries, per-Run Server-Sent Events, generated OpenAPI contracts, and typed problem outcomes. The browser calls Next.js through secure HTTP-only cookies; Next.js calls FastAPI with server-held scoped access tokens. Future direct clients require their own OAuth audience and scopes. Planner and Operator surfaces remain separate; a future Guest surface must also remain separate, but Guest endpoints are deferred from the invitation-only release. Backend modules invoke typed application ports directly rather than calling their own HTTP endpoints.

FastAPI trusts only validated credentials and resolves `(issuer, subject)` to an application principal with current access and scopes. Client-supplied Planner identifiers, ownership, roles, email, actor metadata, and timestamps carry no authority. Operator endpoints administer Invitations and Planner Access Status without exposing Trips. If the deferred Guest surface is later introduced, its endpoints expose no Planner records, saved Trips, Runs, Approvals, or handbooks.

Every mutating command requires an `Idempotency-Key` scoped to the principal, command kind, and target. PostgreSQL retains the request fingerprint and exact original response for the lifetime of the affected Trip or durable record; the same key and payload replay that response, while different content returns conflict. Trip mutations also identify the expected Plan Revision, and other controls identify an expected record version. Stale commands never auto-merge or rebase. Approvals additionally bind the exact Approval Request and reviewed fingerprint.

Bounded local commands return the committed result synchronously. Commands requiring capability execution atomically validate and create a Run, then return `202 Accepted` with the Run identifier, accepted base revision, latest event sequence, and observation location. Synchronous creation returns `201`, bounded updates return `200`, and idempotent replay preserves the original status and body. Each command is one typed application action; only an established cohesive Plan Amendment may contain multiple atomic changes, and there is no generic batch or client-defined transaction.

PostgreSQL stores normalized relational canonical records rather than an event-sourced reconstruction. Canonical identity and access, Trip, Trip Request, Trip Structure, Plan Revision, Evidence, Selection, Approval, and Handbook records remain distinct from durable interaction controls, Turns, Runs, attempts, validated artefacts, events, idempotency receipts, outbox entries, and non-canonical LangGraph checkpoints. A durable record is not automatically canonical Travel Plan state. Each authoritative module owns its writes; cross-module canonical changes pass through the Trip Planning commit coordinator and one shared unit of work. UI, provider, reasoning, and workflow adapters never write canonical tables directly.

Asynchronous acceptance uses one short transaction to recheck access, ownership, idempotency, expected revision, active mutation, and command preconditions and then insert the command receipt, Run, initial public event, and outbox entry. Execution starts only after commit. The committed Run row is the durable queue; an executor loop, initially allowed inside the single backend process, claims work with a bounded lease and heartbeat. Crash recovery creates a new attempt within the same Run. Each Run executes from its immutable accepted inputs, base revision, and fingerprints rather than silently rereading mutable current state.

After a capability returns a complete validated result, the commit coordinator may append immutable deduplicated Evidence in a short transaction without making a Selection or Travel Plan canonical. Reaching an Approval Gate atomically inserts the Approval Request, marks the Run waiting, and writes its event and outbox records. A bound response synchronously rechecks principal, request, fingerprint, revision, and idempotency before recording Approval or rejection and transitioning the Run. Rejection ends the Run as `Cancelled` with reason `planner_rejected`; requesting changes begins a separate amendment flow.

Successful planning commits in one transaction: lock the Trip and Run; recheck the current base revision, single active mutating Run, Planner access, Approvals, Evidence, complete outputs, and fingerprints; insert at most one Plan Revision and its canonical selections; update the current-revision reference; mark the Run succeeded; and append events and outbox entries. A stale base or lost active-Run claim ends as `Blocked` with reason `context_changed` without canonical change; `Superseded` is not a Run state. Suspension requests cancellation and prevents Approval or commit. Cancellation first records `cancellation_requested`; the Run becomes `Cancelled` only after active attempts stop or time out. Terminal Runs never reopen, and retries create linked Runs.

At most one non-terminal mutating Run may exist per Trip, enforced in PostgreSQL. Read-only inspection continues concurrently, but another amendment, regeneration, or planning command fails with the active Run reference instead of being queued. LangGraph checkpoints use separate transactions, cannot override canonical state, and never hold database transactions across provider or model work.

Authoritative queries are pure authorised reads from the PostgreSQL primary and guarantee read-after-write consistency. They neither call external dependencies nor refresh Evidence. Current Trip queries return only the current committed Plan Revision; explicit revision identifiers retrieve immutable history. Run-specific queries may expose validated speculative artefacts only with their Run, base revision, fingerprints, validation state, and terminal reason. The initial release uses direct canonical query handlers rather than asynchronous projections.

Each Run has a durable monotonic event sequence retained for the lifetime of the Run. Authenticated SSE supports `Last-Event-ID`, with a polling query over the same sequence. Delivery is at least once and ordered only within the Run; clients deduplicate by `(Run identifier, sequence)`, and outbox consumers deduplicate by event identifier. Events publish only after their transaction commits, so referenced canonical state is already queryable. Public events contain typed lifecycle changes, safe progress, revision references, and reason codes, never prompts, chain-of-thought, raw external payloads, secrets, or unvalidated claims. PostgreSQL provides the transactional outbox and initial event transport without requiring Service Bus.

External contracts use explicit DTOs rather than ORM or internal domain objects. They use opaque UUIDv7 identifiers, RFC 3339 UTC system timestamps, travel-local date/time with IANA zones, exact decimal strings with ISO currencies, and typed unknown, unavailable, ranged, and not-applicable states. RFC 9457 errors carry stable Flash Trips codes, safe messages, request identifiers, retryability, field violations, and relevant revision or Run references. Closed command and transition enums require versioning; additive diagnostic reason codes require a safe unknown-code fallback. Exact relational schemas, indexes, migrations, and retention remain separate decisions.
