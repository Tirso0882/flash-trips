# Stage security controls by pilot cohort

Flash Trips will stage its security controls across four pilot cohorts: one trusted travel specialist, ten Planners, one hundred Planners, and full production. A control is deferred only when it is policy or administrative lifecycle whose absence changes no schema, no trust boundary, and no browser contract. Controls that establish the identity data model, principal-scoped ownership, the application session boundary, or token validation are never deferred, at any cohort size, because retrofitting them is a migration across every table and query rather than an added feature. Each cohort gate must be met before the cohort grows, not after.

## Considered Options

- Implementing the complete ADR 0014 control set before the first specialist evaluation was rejected because it front-loads seventeen windows of identity administration ahead of any Planner-visible planning behaviour, and a specialist cannot evaluate plan quality against an empty product. The controls deferred here also cannot be exercised or observed with exactly one trusted Planner: cross-Planner denial needs a second Planner, Invitation administration needs someone to invite, and Protective Access Hold needs abuse to contain.
- Deferring authentication entirely for the single-Planner cohort, using platform-level access control such as Container Apps built-in authentication with an implicit single Planner, was rejected because it leaves ADR 0008's Entra-versus-Auth0 decision unproven while the provider choice is still cheap to change, and it defers principal-scoped ownership, which is the one thing that must exist before there is data to own.
- Deferring by calendar or by milestone rather than by cohort was rejected because exposure scales with the number of Planners and the sensitivity of their Trip data, not with elapsed time or feature count.
- Weakening the controls permanently for the pilot was rejected. This decision changes when a control lands, never whether it lands.

## Consequences

The following controls are required at the single-Planner cohort and are not deferrable at any size. External Identities resolve by exact `(issuer, subject)`, never by email equality. Every Trip-scoped table carries its owning Planner reference and every repository is principal-scoped, even while exactly one Planner exists. The browser holds only an opaque, `Secure`, `HttpOnly`, `SameSite` application-session cookie backed by a server-side session record, with allowed-origin validation and a session-bound CSRF token on state-changing requests. FastAPI validates token signature, algorithm allowlist, exact issuer, exact audience, lifetime, not-before, and scope, and rejects an ID token presented as an access token. No token, secret, or private payload reaches any log, telemetry, or evidence channel. The privacy disclosure of data categories, purposes, Sensitive Trip Data risks, provider and model processing, and retention precedes any Trip data collection, because that obligation follows the first real person rather than the tenth.

The single-Planner cohort admits its one Planner through a single-entry External Identity allowlist rather than an Invitation. One sign-in method, Google federation, is sufficient. The negative-token matrix is reduced to the cases that are catastrophic rather than exotic: wrong issuer, wrong audience, token minted for another API, ID token presented as an access token, algorithm confusion, expired, and tampered signature.

Deferred to the ten-Planner cohort: Invitations with their single-use digested secret and exact verified-email match, Operator bootstrap and the separated Operator surface, safe identity linking and unlinking, the session-management surface of session list and revoke-all, Operator-controlled suspension and closure, and the cross-principal denial suite that needs more than one Planner to mean anything. This scope needs no new ticket, but it does not fall on whole tickets either. FT-01 (#198) defers in full. FT-02 (#199) defers in part: the linking half of US-005, the session-management half of US-006, and all of US-007. The other half of those two stories is not deferred and lands now under E-ID (#117), which resolves External Identities by exact `(issuer, subject)` and issues the revocable server-side session behind the opaque application cookie. Registry ownership does not move. FT-02 remains the primary implementation owner of US-005 through US-007, because a story completes when its owning feature completes, and an enabler produces evidence rather than owning a story. What changes is when those stories are scheduled, moving them from prerequisites of the specialist evaluation to prerequisites of admitting a second Planner. Slice 1's product work cannot sit behind that gate, so FT-03 (#204) is blocked by E-ID rather than by FT-02, and US-008 (#182) follows the same edge instead of waiting on an Invitation and an Operator suspension that do not yet exist. The single-entry External Identity allowlist that E-ID leaves in place is removed when FT-01 makes Invitations authoritative.

Deferred to the one-hundred-Planner cohort: abuse controls and rate-limit calibration, Protective Access Hold and abuse-driven containment, incident containment with safe health reporting, Planner personal-data export and deletion, and security alert delivery. These remain owned by their existing Slice 7 and Slice 8 stories rather than moving.

Deferred to full production, unchanged from ADR 0014: the drill list covering session and identity revocation, Operator recovery, secret and key rotation, adapter kill switches, critical safe mode, known-good deployment, and backup restore with deletion replay, together with independent security review, a verified backup restore, and release gating. E-RECOVERY (#166) and the Slice 8 stories already sit at this gate.

This decision narrows the timing of ADR 0014's requirement that registration and CI carry the complete authorization matrix, adversarial fixtures, abuse controls, and retention and deletion recovery. It does not narrow the content. Those requirements bind at the cohort gate that introduces the exposure they address, and every one of them still binds before invitation production. ADR 0014's clause text stands; if a later reconciliation wants this staging enforced as a formal supersession rather than a timing refinement, that belongs in the E-DECISIONS conflict ledger.

Cohort growth is a gate, not a date. Admitting the second Planner requires FT-01 and FT-02 to have passed, and admitting the eleventh requires the one-hundred-Planner controls. A cohort that grows before its gate passes is operating outside this decision, and the deferral it relied on is void. Because exposure is what is being staged, the single-Planner cohort holds only that Planner's own or synthetic Trip data, and no third party's Sensitive Trip Data enters the pilot before the Invitation and deletion controls exist.
