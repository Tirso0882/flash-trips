# Prove the product path with a walking skeleton

Flash Trips will build one thin, permanent, end-to-end path through the product before building any station of that path well. The path runs sign-in, Trip creation, a Run, a committed Plan Revision, an Approval and a Handbook download, with fixture-backed results at every station, and it is asserted by a single browser journey test that runs against a real browser and real PostgreSQL. E-SKELETON (#261) delivers it. FT-04 through FT-22 then deepen each station against a running system instead of constructing one. The journey test and its Evaluation Fixtures are permanent; the thin implementations behind them are deliberately temporary and are replaced in place.

This decision reorders existing work. It adds no product scope, changes no acceptance criterion, and moves no registry ownership.

## Considered Options

- Continuing to complete each trunk Feature before starting the next was rejected on measurement. The native `blockedBy` graph made the trunk a near-total chain: a Handbook was thirteen Features deep from the merge of E-ID, invitation-production release was twenty-two deep, and only two of forty-five open Features had no blockers at all. At E-ID's observed rate of roughly six Tasks per Feature, that ordering puts the first end-to-end evidence at E-ACCEPTANCE (#165), position twenty-one of twenty-two. A product whose central claim is an evidence-backed Travel Plan would not have produced one, through any path, for months, and the seams between stations would be unexercised the entire time.
- Deleting blocking edges without building a skeleton was rejected because most of those edges are real at the depth the tickets are specified to. FT-05 genuinely needs FT-04's Trip Request update before it can preserve Trip Structure across one. The edges are only removable once a thin version of each station exists, so the skeleton is what makes the graph thinnable rather than an alternative to thinning it.
- Splitting each trunk Feature into a thin ticket and a deep ticket was rejected as a worse form of the same idea. Under this repository's supersession rule, re-specification closes and replaces tickets rather than editing them, so this would have closed and rewritten about a dozen Features to express what one enabler expresses. E-ID already set the precedent for the cheaper shape: an enabler lands the thin substrate while the Features above it keep owning their User Stories and get rescheduled by ADR 0019.
- Making the skeleton throwaway, deleted station by station as each real Feature landed, was rejected because the journey test is the artefact worth keeping. Its value is that it stays green through every later change, which is precisely what deleting it forfeits.
- Keeping the thin implementations permanently, as fixture-backed Capabilities retained for testing, was also rejected. That leaves a live code path capable of producing a Travel Plan with no Evidence behind it, which contradicts ADR 0002's separation of proposal from authority and the product's own central claim. The fixtures are permanent because `CONTEXT.md` already gives Evaluation Fixture a versioned, provenance-bound home. The stubs are not.
- Asserting the journey at the HTTP layer rather than through a browser was rejected because the Next.js BFF to FastAPI hop is the least exercised seam in the system and the one most likely to be silently broken. An HTTP-level journey would skip exactly the integration the skeleton exists to prove.

## Consequences

Six properties are established at the skeleton and are never deferred, because each is a migration across every table and query afterwards rather than an added feature. Trip Structure is multi-city-shaped from its first row, with the single city stored as a one-element collection of stays, satisfying US-012 without a later data-model change. Plan Revisions are immutable on first write, per ADR 0003. Every claim carries a slot for its Evidence and observation time even while every value is a fixture, because provenance cannot be attached later to data recorded without it. Ownership resolves from the authenticated principal on every read and mutation, in the principal-scoped repository pattern E-ID established, never from a client-supplied identifier. Provider and model text enters as untrusted at every boundary that accepts it. Approval is reachable only through a typed action bound to an exact subject, never through free text.

The `Capability` contract is declared in `flash_trips.kernel`. This placement is forced rather than chosen: `.importlinter` forbids `flash_trips.capabilities` from importing `flash_trips.application`, `flash_trips.adapters`, or a sibling capability, while `flash_trips.application` may import capabilities and `flash_trips.kernel` is importable by both and imports nothing. Declaring the contract in `application`, alongside the existing `ServiceStatusPort` and `AccessTokenVerifier` ports, would leave a protocol the implementing capability cannot import and could therefore satisfy only structurally, with no enforcement at its own site. Eight trunk Features are capability work, so this contract is the most durable thing the skeleton produces.

The journey is extended by exactly one station per Task and is green when each Task closes. This is the property that separates a walking skeleton from a large feature with a test at the end, and it is why E-SKELETON is a chain of seven Tasks rather than parallel work. The chain is deliberate here and is not evidence that the trunk chain was correct.

A browser harness is introduced where none existed. Playwright was present in `pnpm-lock.yaml` only as an optional peer dependency of Next.js, with no configuration, script, browser binaries or test directory, and every prior test ran in process. The journey becomes a required CI check running against real PostgreSQL, with no SQLite or in-memory substitution, consistent with the existing Slice exit criteria and #165's stance.

Registry ownership does not move. E-SKELETON owns one `kind: "enabler"` requirement and no User Story, exactly as E-ID, E-SCAFFOLD and E-ACCEPTANCE do, because an enabler produces evidence rather than owning a story. FT-03 remains the primary implementation owner of US-008 through US-010, FT-14 of the single-city plan stories, FT-21 of the Approval stories and FT-22 of the Handbook stories. What changes is when those Features are scheduled and how much each has left to do when it starts.

Two things follow that this decision does not itself perform. The trunk's blocking edges are re-pointed only after the skeleton lands, when a thin version of each station exists to make the re-pointing safe, and that pass is a separate change. And the deepening Features remain fixture-backed until the pilot outgrows two Planners: live providers, Reasoning Profiles, Azure provisioning and the release pipeline stay at their existing cohort gates under ADR 0019, whose staging logic this decision extends from security administration to delivery order.

Every thin implementation carries an in-code marker naming the Feature that replaces it, and a test asserts each marker names an open issue. This is what stops the skeleton from being mistaken for the product.
